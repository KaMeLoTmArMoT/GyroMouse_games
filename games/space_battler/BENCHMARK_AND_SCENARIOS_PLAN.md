- **Combat Golden Set, Telemetry Inspector & Scenario Plan**
  - **Recommendation:** benchmark the actual TypeScript combat engine in Node; add opt-in structured telemetry; establish behavioral gates before optimizing balance. Keep Python as an optional optimizer/report consumer, not a competing combat authority.
  - Audit baseline: `cbd95ee`, inspected 2026-11-05. Validation: `npx --no-install vitest run tests/simulation.test.ts --reporter=dot` in `frontend/`: **56 tests passed, 17.34 seconds**. This is test-suite wall time, not a measured simulation speedup. No new tournament or browser playtest was run; proposed balance bands and new preset pairings below are hypotheses.
  - Notation: **BB** battleship, **CR** cruiser, **CV** corvette, **SC** strike craft. Current complete-ship prices: BB 3,200; CR 1,100; CV 350; SC 120 credits. Weapon `cost` fields are not additional fleet charges.

- **1. Audit findings → architectural consequences**
  - **[Authority] The active game is already headless-compatible.** [App.tsx](frontend/src/App.tsx), `assembleSimulation`, builds fleets at x = −800/+800 through [fleetBuilder.ts](frontend/src/engine/fleetBuilder.ts). [simulation.ts](frontend/src/engine/simulation.ts) imports only engine utilities/types; rendering/audio are optional callbacks. Import these modules directly in a CLI; no canvas, React, browser automation, server, or physics rewrite is required.
  - **[Tournament validity] The Python “Monte Carlo” runner is repeated deterministic evaluation.** [tournament.py](backend/src/balance/tournament.py), `run_balance_tournament`, runs six cross-archetype pairings of 1 BB / 3 CR / 9 CV / 25 SC. Its ten rounds use identical positions, no seed variation, no side swaps, a 60-second cutoff and 1/30-second steps. Draws/timeouts disappear from the denominator; all-draw returns 0, resembling total defeat. It reports only A's decisive win fraction; there is no optimization loop or grid search here. Replace these semantics in the new runner rather than expanding this simulator.
  - **[Simulation drift] Python and TS now model materially different games.** [Python simulation](backend/src/engine/simulation.py) uses one ship target, sequential movement/fire, approximate lead, 250/600-unit movement bands, a simple BB 90° turn, hitscan PD with 6× missile damage, and no fighter wings, escort stations, arena containment, or ship contact. TS uses fixed 1/60 ticks, staged movement/fire decisions, independent mount targets, quadratic intercepts, moving-target sweeps, physical proximity flak, fighter mission/recovery/dogfight phases, escort reassignment, and timed capital maneuvers. Both currently fly missiles ballistically after launch; target IDs do not imply homing.
  - **[Data drift] Constants alone cannot restore parity.** [Python ship_factory.py](backend/src/engine/ship_factory.py) gives BB speed 45, armor/hull 1,600/2,200, recharge delay 0 and spinal arc ±90°; the active builder uses 38, 1,800/2,500, delay 1.5 and ±7.2°. Python factories also leave both teams at heading 0. Python projectiles reconstruct weapon definitions by type; TS preserves shot-time profiles. Python `take_damage` returns raw input despite its effective-damage docstring.
  - **[Duplicated specifications] The frontend UI is also stale.** [FleetBuilder.tsx](frontend/src/components/FleetBuilder.tsx), `HULL_SPECS`, advertises a 180-damage/980-range BB rail versus the active 260/1,350, and 18-damage fighter plasma versus 120. [testFleets.ts](frontend/src/engine/testFleets.ts) is another older factory with no caller found in the inspected source. The backend README claims client JSON consumption, but active assembly uses inline TS data. Extract one hull/mount definition source for assembly, displayed stats, price totals and tuning; do not export old Python values over it.
  - **[Existing coverage] Extend the real tests.** [simulation.test.ts](frontend/tests/simulation.test.ts) already covers fixed-step equivalence, capital mirror ordering, flak/interception, independent broadsides, arena recovery, fighter pass completion, 60-SC attacks, 2-BB superiority and CV-carousel resolution. The nested frontend has Vitest installed but no `test` script; root instructions saying “no test runner” do not describe this package. Preserve small mechanic tests; move shared scenario construction into reusable fixtures without discarding their assertions.
  - **[Telemetry gap] Current totals cannot explain losses.** `stats.damageDealt` rounds each weapon damage application and includes shield/armor/hull depletion; `resolveShipCollisions` directly changes defenses and can instantly kill SC against capitals without recording damage totals. `destroyShip` counts losses but lacks source/weapon attribution. `combatLog` is capped at 30 entries and uses random IDs. The UI's copy-telemetry action is a selected-ship snapshot, not a battle history.
  - **[Scenario contracts] Orders and outcome handling need explicit boundaries.** `orders` is keyed only by `groupId`, so teams sharing groups can receive each other's orders. Current presets contain composition, not doctrine, and assembly sets no orders. Make order identity `(team, groupId)` before running independent doctrines. `winner` remains null after mutual destruction; ticks continue after a win. The runner must classify terminal states itself and explicitly stop.
  - **[Presets] Eleven entries mix debugging and discovery.** [fleetPresets.ts](frontend/src/engine/fleetPresets.ts) contains the standard fleet, six pure-class sizes and four mixed fleets. Budgets currently match complete-ship costs, but “12 fighters in 4 wings” disagrees with the current automatic split into two wings of six; “30 fighters overwhelm capitals” is an unverified promise. `test_all_threes` is referenced by a combat regression: preserve that fixture/ID when reorganizing the picker.

- **2. Golden Set runner: small, reproducible, engine-native**
  - **Files and shared contract:** add `frontend/src/engine/scenarios.ts` for typed scenario data and a pure assembler shared by App/tests/CLI; `frontend/src/engine/combatTelemetry.ts` for optional observer types; `frontend/bench/{run,inspect,report}.ts` for Node-only execution, diagnostics and output. Keep Node imports out of engine modules. Start with `tsx` as a small development dependency for extensionless TS imports; keep Vitest for assertions.
  - **Scenario definition:** stable ID/version/tags, both compositions with team-local groups, initial orders, spawn recipe/explicit overrides, layout seed, duration limit, expectation IDs and provenance. Include optional reference Blue fleet for a featured Red preset. Generate stable IDs matching the factory's numeric suffix convention: AI uses suffixes for station/escape choices. Record resolved positions, headings, mounts, cooldowns, anchors and orders, not just counts.
  - **Execution:** fresh ship objects and simulation per run; call `update(1/60)` in an integer tick loop without sleeps. Use 180 simulated seconds by default, 240–300 for tagged long regressions; retain existing fixture horizons. Stop on extinction, mutual destruction, duration limit, invalid state or wall-time cancellation. Label timeout as censored/unresolved, not a winner based on remaining HP. Freeze results at first extinction, following the engine's victory criterion (the UI itself keeps ticking); any projectile-drain endgame must be a separately versioned policy.
  - **Speed:** “100×” means simulated seconds / timed wall seconds. Larger `dt` does not skip work: `update` still performs 1/60 ticks and caps catch-up at 240 ticks per call. Warm Node once; measure execution separately from startup/reporting, with telemetry enabled and disabled. Report per-scenario speed, peak ships/projectiles, total suite wall time and hardware/runtime. Aim for ≥100× on representative small/medium matches; establish a separate swarm budget after measuring 60–120-SC cases.
  - **Scaling:** begin serially; then use a bounded persistent worker pool across independent battles, deterministic result sorting and a fixed worker count. Profile before optimizing: fighter 16-sector scoring scans ships/projectiles, focus scoring repeatedly scans peers, and cruiser clearance can perform many pairwise passes. Cache immutable definitions and unchanged match results; spatial indexing comes only if measured costs justify it. Do not change tactical cadence to make benchmark numbers look faster.
  - **Reproducibility:** a seed selects documented initial-layout perturbations, not invented combat RNG. Keep nominal UI assembly as a separate fixture; add bounded y/heading variation and validate arena/spawn clearance, including hostile overlap. Existing same-team swarm packing tests do not establish safe opposing-swarm deployment. Store the resolved layout and perturbation algorithm version; reject invalid generated layouts deterministically. Replace cosmetic random log IDs with a sequence, or exclude them from combat-state hashes; avoid globally replacing `Math.random`.
  - **Fairness:** evaluate each cross-class pairing both ways using the same transformed layout, preserving hull chirality under a 180° rotation. Also test team-label exchange and reversed insertion order independently; do not assume full permutation invariance from the existing capital test. Stable ID tie-breaking and sequential phase mutations can still matter. Keep these diagnostic transformations distinct from ordinary seed samples.
  - **Run tiers:** smoke = canonical fixtures and critical regressions; tune = affected matchups with 4–8 fixed paired layouts; full = all matchups with 16–32 paired layouts plus held-out seeds. Repeated identical battles test determinism only. Paired orientations are correlated: aggregate/estimate uncertainty by layout pair, not as independent trials.
  - **Proposed workflow, from `frontend/`:** `npm run bench -- --suite smoke`; `npm run bench -- --suite golden --seeds 16 --workers 4 --out artifacts/golden`; `npm run bench -- --scenario swarm60-triple --seed 7 --trace`; `npm run bench -- --compare artifacts/baseline/results.json artifacts/golden/results.json`. These commands require implementation; output directory creation belongs to the runner.
  - **Outputs:** compact console table of result/duration/remaining value/alerts; versioned JSON as the authoritative dataset; Markdown comparison ranked by severity and regression size. Include engine commit plus dirty-source hash, definition hash, scenario/expectation versions, Node version, seed/layout, step/stop policy and instrumentation mode. Trace only failures on deterministic rerun, with a bounded pre-alert buffer and explicit trace truncation; offer a full trace for one selected battle. Exit nonzero for hard failures or incomplete execution; soft balance warnings remain visible and can be promoted in CI.

- **3. Telemetry and expectation model**
  - **Instrumentation contract:** add an optional read-only observer at actual decisions and mutations, with tick/time and source ship/mount/projectile/target IDs. Capture shots, impact/intercept/expiry, defense deltas, regeneration, contact entry/exit, deaths and target/phase changes. Add mount ID provenance to projectiles and beam damage calls. Aggregate counters immediately; sample trajectory/state summaries at 5 Hz. Exact damage/contact counters stay tick/event-based. Avoid monkey-patching private methods or reconstructing kills from final positions.
  - **Damage accounting:** record unrounded actual shield, armor and hull depletion by team/class/group/ship/mount and weapon versus ram/forced-contact death. Capture the entire hull delta of lethal fighter contact, without changing its gameplay semantics. Record shield regeneration separately; `initial + regenerated − actual depletion = final` per layer is an accounting invariant. Raw fired damage, mitigated damage and overkill are separate quantities. Existing rounded UI totals remain labeled legacy totals until migrated.
  - **Battle value:** report W/L/mutual-destruction/timeout separately; survivor counts by class; remaining shield/armor/hull; first shot/hit/kill; duration; credited kills and damage efficiency per initial credit. Also report remaining live cost and a health-weighted residual value using fixed reference costs and armor/hull fractions. Shield damage farming must not masquerade as progress or remaining combat strength.
  - **Containment:** maximum and p95 center radius, ship-seconds beyond imported `ARENA_RADIUS = 1350` and `ARENA_HARD_PULL_RADIUS = 1550`, longest outside excursion and inward recovery time. Initially use the existing `<1650` bound only for its covered layouts; treat a brief crossing of 1550 as recovery behavior, not automatically an off-map bug. Hard finite-state checks apply everywhere.
  - **Ramming:** unique contact episodes, duration, pre-resolution closing speed, direct layer loss and deaths by hull pair/team. Identify SC→hostile-capital shield contacts explicitly; use contact hysteresis to avoid counting every tick as a new ram. Track near-misses separately. The current 60-SC test's proximity-based `contacts <= 2` is not equivalent to two actual rams and must be rebaselined when exact events exist.
  - **Weapons:** per mount shots, hits, projectile expiry/interception, damage and longest ready-but-idle interval. Record the acquisition funnel: no legal enemy → role/phase exclusion → range → current/led arc → unreachable intercept → tracking → cooldown. Reuse the actual predicates and only gather expensive rejection details in diagnostic mode. Report opportunity time and time wasted ready despite a feasible target; do not divide by all battle time and call it AI utilization.
  - **Broadsides:** port/starboard damage and firing opportunities separately, bow-acquire/hold/reacquire dwell, and main-gun shot intervals. A rear-facing battery with no target is not broken; `max_range` intentionally forgoes some beam opportunities. Diagnose poor presentation from in-range-but-out-of-arc time, and fire-control failure from eligible-but-idle time.
  - **Target/wing health:** voluntary switches per engaged minute and median lock duration, excluding dead/invalid targets and urgent missile defense; navigation, wing mission, dogfight and mount targets separately. Track attack passes, mission-shot completion rate, recovery/staging dwell, dogfight interruptions and shots before death. Escort diagnostics add anchor changes, leash/station distance and threatening missiles intercepted versus leaking through.
  - **Stalemate classifier:** after initial approach, flag a 20-second window with no kill and <1% combined initial armor+hull depletion. Split it into no-fire deadlock, shield-regeneration equilibrium, or carousel: repeated target-relative winding/range recurrence with low net progress. Require an additional window before escalating; periods are initial tunable thresholds. Orbiting while dealing meaningful damage is healthy. Do not terminate balance runs early on this heuristic until validated against legitimate recovery cycles.
  - **Hard expectations:** finite positions/velocities/defenses, valid unique entity IDs and team-scoped orders, bounded defense layers, accounting reconciliation, exactly-once deaths/interceptions, deterministic replay, and existing mechanic-specific contracts. Qualify spawn/collision displacement assertions so legitimate contact correction is not mistaken for teleporting. Keep balance failures distinct from implementation corruption.
  - **Soft expectations:** winner leaning or contested; explicit draw/timeout ceilings; duration, survivor, hull-retention and layer-damage bands; contextual behavioral limits. Store lower/upper bounds, scope/denominator, severity, rationale and status: `existing-regression`, `design-hypothesis`, or `measured-baseline`. Bootstrap measured quantiles from accepted layouts, inspect outliers, then freeze versioned bands. Never silently bless the current output as the desired balance.
  - **Starter calibration:** contested pairs target a resolved score of 0.35–0.65; intended counters 0.65–0.85. Score = `(wins + 0.5 × mutual destructions) / resolved runs`, or null with zero resolved runs; always show timeout fraction. Excessive timeouts invalidate the claim. Treat bands as design targets, not precise estimates from four seeds. Deterministic seed variability measures positional robustness, not random hit chance. Preserve counter relationships rather than forcing every pair to 50/50.
  - **Root-cause report:** show expectation, measured value, baseline delta, affected entities, first divergence time and reproducible command. Rank evidence-backed hypotheses: low SC damage + many failed passes + capital-contact deaths → unsafe ingress; no rams + long recovery/phase rejection → mission starvation; ready broadside + range/arc rejection → positioning; high CV angular travel + shield depletion canceled by regen → carousel equilibrium. Label diagnoses as hypotheses and attach the evidence window; do not assert causality from a winner alone.

- **4. Golden Set matchup matrix**
  - **Exhaustive 3-v-3 core:** ten unordered cells including mirrors generate all **16 ordered class matchups**. These are equal-count behavioral probes, not equal-budget balance tests. The six off-diagonal expectations below start soft; run side swaps and layout variants.
    - **BB–BB:** symmetric attrition; both side batteries and rails participate over time; no persistent side advantage. Mutual destruction is a valid outcome.
    - **CR–CR:** active torpedo/beam exchange during oblique movement; avoid no-fire range equilibrium.
    - **CV–CV:** stable orbit with irreversible attrition; existing canonical regression resolves within 150 seconds with ≥4 total losses.
    - **SC–SC:** dogfight acquisition and repeated firing; existing 3-v-3 test requires casualties and every surviving fighter having fired by 60 seconds, not a guaranteed winner.
    - **BB–CR:** BB favored at 9,600 versus 3,300 credits; preserve rail/broadside tempo against maneuvering torpedoes.
    - **BB–CV:** BB favored by budget; expose whether evasive CV can stall forever and whether secondaries actually acquire them.
    - **BB–SC:** BB survival favored at 9,600 versus 360; require surviving SC to attempt productive passes rather than idle or ram. This is not a swarm-counter test.
    - **CR–CV:** CR favored at 3,300 versus 1,050; CV should close and intercept, with measurable armor pressure where opportunities exist.
    - **CR–SC:** CR favored at 3,300 versus 360; assess lead accuracy versus evasive passes and beam usage.
    - **CV–SC:** CV favored as an anti-fighter counter; SC still get a survival/attack window. Retain the separate stationary one-CV fixture's 2.5–4 seconds from first hit to fighter death.
  - **Budget/role layer:** use nominal factory deployment and paired perturbations; no unmeasured win guarantees.
    - **1 BB vs 3 CR (3,200 / 3,300):** costly near-peer duel. Existing 120-second fixture resolves, loses ≥2 CR, and leaves BB total defenses below 50%; winner unspecified. Preserve this exact fixture alongside broader contested hypotheses.
    - **2 BB vs 3 CR (6,400 / 3,300):** superiority regression; existing seeds 1/7/29 require BB victory by 240 seconds, both BB alive with each >50% hull. Also run the side-reversed case.
    - **3 CV vs 1 CR (1,050 / 1,100):** missile denial versus beam attrition; existing 60-second fixture reaches <300 separation and removes >20% CR armor. Learn the terminal winner before adopting a counter claim.
    - **9 CV vs 26 SC (3,150 / 3,120):** screen specialization under equivalent spending; CV-favored hypothesis, report flak overlap and SC opportunities.
    - **1 BB vs 27 SC (3,200 / 3,240):** unescorted-capital saturation; SC pressure hypothesis, measure repeat passes and critical mass rather than mandate a victory.
    - **3 CR vs 27 SC (3,300 / 3,240):** mobile capitals versus dispersed plasma; contested discovery case and long-range drift detector.
    - **1 BB + 3 CV vs 35 SC (4,250 / 4,200):** quantify escort protection versus the unescorted case. Also run identical 35-SC opponents against 1 BB alone as a marginal-escort experiment; label its budget imbalance.
    - **3 CR + 3 CV vs 1 BB + 9 SC (4,350 / 4,280):** screen survivability versus fighter distraction and heavy fire; likely doctrine-sensitive, outcome to calibrate.
  - **Swarm/regression layer:** **12 SC vs 12 SC**, **3 CR vs 20 SC**, and **60 SC in three groups of 20 vs Triple Threat (3 BB + 3 CR + 3 CV + 3 SC)**. Preserve the latter's existing 90-second checks: >6,500 legacy weapon damage, ≥5 Red losses and ≥1 capital kill; this 7,200-versus-14,310-credit test measures contribution, not expected SC victory. Add 120-SC deployment/performance stress separately, without balance assertions.
  - **Tactical layer:** both teams **1 BB + 3 CV** for screen-clinch checks; the six featured pairs below; matched compositions under `brawl`/`optimal_range`/`max_range`; grouped versus single-group SC; and controlled anchor-loss fixtures for escort reassignment. Define initial geometry for flank variants explicitly—extra group IDs alone do not implement flanking routes.

- **6. Sample-efficient balancing beyond grid search**
  - **Optimize behavior first, economics second.** Reject hard-invalid candidates and retain per-scenario losses. A single scalar can hide a broken matchup. For valid runs use weighted squared distance outside desired outcome/margin bands, plus timeout, behavioral-regression and parameter-change penalties. Use fixed reference prices for health-weighted margins during stat tuning; never let a candidate improve its score merely by changing its own price. Normalize components to comparable scales and keep design targets fixed across a search.
  - **Primary method: bounded SPSA for 4–8 continuous parameters.** Normalize/log-scale positive parameters, constrain them to design-approved bounds, and freeze discrete architecture. At iteration k, draw seeded ±1 vector Δ, evaluate the same affected scenario/layout batch at `θ + cΔ` and `θ − cΔ`, estimate `g_i = (L+ − L−)/(2cΔ_i)`, then project `θ − ag` into bounds. Decay a/c gradually; preserve the best independently checked candidate rather than assuming every noisy step improves it.
  - **Concrete evaluation budget:** 12 SPSA updates = 24 objective evaluations; baseline + four incumbent checks + six local refinement probes + one held-out validation = **36 objective evaluations**. Each objective may contain eight affected matchups × four layouts × two orientations = 64 battles; this example is **2,304 battles**, not 36 battles. A final full-Golden run is additional. Cache unaffected old-v-old results only when engine/definitions/scenarios are unchanged. Common layouts reduce gradient noise; held-out layouts detect positional overfitting. This is a bounded search experiment, not guaranteed convergence.
  - **Price calibration:** cost alone does not affect fixed-composition combat, so its combat gradient is zero. After stat selection, bracket break-even new-hull counts against several fixed-budget reference fleets, reuse cached combat results, and estimate implied unit prices from `reference budget / break-even count`. Combine role-weighted anchors robustly, retaining a price interval when integer fleet sizes skip parity. Then validate actual near-budget compositions at nearby rounded prices; changed counts require new simulations. Include escort marginal value, not only solo duels.
  - **Bradley–Terry/Elo:** useful as a regularized summary of resolved fleet comparisons and an initial strength/cost prior; explicitly handle draws and exclude/report censored outcomes. A scalar rating cannot represent cyclic counters or mixed-fleet synergy and is not automatically a fair price. Use matchup residuals and marginal escort experiments alongside it. Avoid forcing a hull to break even against its intended counter.
  - **Alternatives:** bounded coordinate search is simpler for ≤3 parameters and a useful final refinement. Nelder–Mead can stall on discontinuous winner plateaus; continuous residual-health margins help. CMA-ES becomes attractive for strongly coupled, larger searches but spends multiple candidates per generation; do not promise it will finish in a few dozen battles. Start with SPSA plus a small local refinement, not a generic optimization framework.
  - **New-hull prerequisites:** the current `HullClass` union, builder filters, capital classification and `capitalIntent` BB-versus-CR branch do not support an arbitrary new hull. A Missile Frigate's lateral launch salvos need explicit mount/salvo semantics; tune missile damage, interval, projectile speed and survivability after validating their firing opportunities. A Broadside Dreadnought needs a maneuver profile that values both banks rather than `.find()` selecting one spinal/missile as the maneuver clock; test enemies on both sides and bank reacquisition first. Keep integer salvo size, arc topology and role design fixed during continuous tuning; compare a few discrete designs separately.
  - **Python's pragmatic role:** preserve independent utilities such as [hull_geometry.py](backend/src/balance/hull_geometry.py). Label the old tournament historical and correct its README claims. If scientific optimization is needed, Python can exchange versioned candidate/result JSON with a persistent Node runner under `uv`; it should never evaluate candidates through the old Python combat engine. Apply accepted parameter patches explicitly with a report, not by silently rewriting production definitions.

- **7. Implementation sequence and acceptance checks**
  - **1 — Shared scenario assembly + CLI skeleton.** Reuse active builder and fixed ticks; add explicit result/stop categories, metadata, nominal/paired layouts and smoke output. Verify replay equality, mutual destruction classification, and CLI/App assembly equality. Establish measured small/medium/swarm throughput before making speed promises.
  - **2 — Trustworthy telemetry.** Instrument actual firing, defense/regen/contact/death events and add provenance. Verify exact accounting, one death/interception event, contact-induced SC hull loss, and identical combat outcomes with telemetry on/off. Add concise failure traces and acquisition-reason diagnostics.
  - **3 — Golden registry and expectations.** Promote existing regression fixtures; enumerate all 16 ordered 3-v-3 cases plus asymmetries/swarms. Scope orders by team and test independent opposing doctrines before enabling stance variants. Run baseline/side-swap/held-out layouts, investigate anomalies, then freeze reviewed bands. Make hard smoke gates CI-fast and full sweeps a separate job.
  - **4 — One specification source.** Extract current TS hull/mount data without changing values, derive UI/preset budgets from it, and add isolated candidate overrides. Verify factory snapshots and battle results remain equivalent; a candidate must not leak into later runs. Correct stale displayed descriptions and backend export claims.
  - **5 — Curate the picker using evidence.** Evaluate the six suggested pairs, retain only healthy tense encounters, preserve diagnostic IDs and `test_all_threes`, and add suggested-Blue/copy/rerun actions. Verify group composition, prices and saved preset resolution; visually review featured encounters when a browser/dev session is requested.
  - **6 — Tune a new hull as a controlled experiment.** Implement its weapon/maneuver contract, choose 4–8 bounded parameters, run the 36-evaluation pilot, calibrate cost, then validate the full Golden Set and held-out layouts. Acceptance: better target loss with no hard failures or unacceptable counter/behavior regression. Add in-app Worker quick-sim only after this shared runner/report contract is stable.
